# Announcements

<!-- <relnotes for announcements go here> -->

* Drake now officially supports macOS 27 Golden Gate ([#25156][_#25156]).
* Drake now uses x86-64-v2 as the minimum target microarchitecture on x86-64
  ([#25051][_#25051]).
* Drake now offers a build option `DRAKE_TEXT_LOGGING` for opting-out of spdlog
  in order to log directly to stderr ([#25152][_#25152]).
  * This splits out the Bazel flag for "use spdlog" vs "which spdlog"
    (dropping the experimental "disabled" option).
  * Wheel (pip) builds use the opt-out while still routing logs to Python's
    built-in logging module.

# Breaking changes since v1.58.0

<!-- <relnotes for breaking-changes go here> -->

* When installing Drake via pip, users who need `MosekSolver` must now opt-in
  to the `[mosek]` extra to request installing Drake with MOSEK support
  ([#25220][_#25220]).
* `MultibodyPlantConfig.use_sample_output_ports` has changed its type to a
  `std::variant` ([#25218][_#25218]).
  * The setting is no longer ignored for a continuous-time plant. Instead, the
    `Unchanged` option (the new default) can be used to indicate that the plant
    setting should be left alone.
  * Users with a config file that previously set both `time_step: 0` and
    `use_sampled_output_ports: true` should change the `true` to either `false`
    or `!Unchanged {}`.
* Implementations of `planning::DistanceAndInterpolationProvider` must implement
  the new method `DoComputeConfigurationDeltas`; no default implementation is
  provided ([#25115][_#25115]).
  * See `//planning/linear_distance_and_interpolation_provider.cc` for an
    example implementation of the new method.
* When using `NloptSolver`, exceptions thrown by costs and constraints were
  previously swallowed but are now rethrown from `Solve()` with their message,
  matching SnoptSolver ([#25079][_#25079]).

Refer to our [Drake Stability Guidelines](/stable.html) for our policy
on API changes.

## Multibody Dynamics and Geometry

<!-- <relnotes for geometry,multibody go here> -->

* [newly deprecated fix] TBD [multibody,examples] [CENIC] Report ICF forces from a continuous plant via sampled output ports ([#25147][_#25147])  # CenicIntegrator solves a convex ICF problem each step instead of integrating the plant's own continuous contact model, so the plant's live dynamics output ports (reaction_forces, contact_results, generalized_acceleration, generalized_contact_forces, net_actuation) disagree with the simulated trajectory. Report the forces of the solve that produced the current state instead, reusing the sampled-output-port machinery that discrete plants already have. Plant (multibody/plant): - SetUseSampledOutputPorts(true) is allowed on a continuous-time plant. It is an opt-in made before Finalize(), which declares the DiscreteStepMemory abstract state. The sampled calc paths serve continuous plants from that memory. - DiscreteStepMemory::Data gains a contact_results field (continuous plants only). CalcReactionForces is split so the inverse-dynamics half is reusable, and is exposed to CENIC through MultibodyPlantIcfAttorney. - A continuous plant has no step of its own, so if no integrator has recorded a sample, its dynamics output ports throw instead of reporting zeros (a discrete plant still reports zeros before its first step). That is how a sampled plant under an integrator that never records fails fast: the first read of a dynamics port throws, naming both remedies. The plant only knows whether a sample exists, not what an integrator is. CENIC (multibody/cenic, multibody/contact_solvers/icf): - Initialize() writes an empty sample (correctly sized, all zeros, no contacts) as its last action, so the sampled ports report zeros until the first step, as for a discrete plant. Every Initialize() starts over from it. Costs, documented: reading a dynamics port before Initialize() throws, and the sample lives in the Context, so after replacing CENIC with a nonrecording integrator (or cloning the Context for one) the ports keep reporting the last recorded sample. - Each accepted solve records the constraint impulses divided by that solve's time step (the second half step in error-controlled mode), with the resulting accelerations, joint reaction forces, contact results and net actuation. A retried step restores the sample from before the failed trials. - When joint locking reduced the problem, contact, weld, ball and distance impulses come from the reduced model that advanced the state, and gain, limit and coupler impulses from the full model. Patches that reduction dropped are reported from the full model's regularized impulse. - IcfBuilder now takes its contact set from the plant's cached GeometryContactData instead of making its own SceneGraph query, so a system that also reads the plant's contact results no longer triggers a second query per step, and hydroelastic contact surfaces have a shared backing store. This applies to every CENIC user, sampled or not. The plant's cache omits contacts between bodies that have no dofs (locked joints); those had no effect on the solution. Trajectories were bit-for-bit identical in the scenes we compared (point and hydroelastic contact, with and without a locked joint). - The actuation matrix is now a dof index table; plants with several actuators on one joint, or with no continuous state, are rejected when ports are sampled. - Retry bookkeeping is reset on Initialize(). - Known approximation: external spatial forces are applied at the start state, so a stiff velocity-dependent force can report a fictitious reaction on joints that should transmit nothing (documented, with an example). Configuration: - MultibodyPlantConfig::use_sampled_output_ports (a bool or Unchanged) now applies to continuous plants, so YAML can request sampled ports for CENIC. Deprecating CENIC with a plant that does not have sampled output ports is left to a follow-up change.

## pydrake bindings

<!-- <relnotes for bindings go here> -->

* [fix] TBD [pydrake] Fix DrakeGymEnv ignoring the info_handler argument ([#25228][_#25228])  # The constructor checked `info_handler is callable(info_handler)`, which compares the handler against a bool and so was never true. As a result, any user-provided info_handler (including the one in the cart-pole example) was silently replaced by a handler that returns an empty dict. Use the handler when it is callable, default to the empty dict when it is None, and reject non-callables with a ValueError (matching the existing reset_handler check). Also fix an RST typo in the docstring.
* [fix] TBD [pydrake] Fix reference cycles in LCM and DiffIK callbacks ([#25196][_#25196])  # Part of the issue "investigate uses of WrapCallbacks() for memory leaks". Python callables stored inside C++ objects are strong references that Python garbage collection cannot see, so a callable that captured its owner kept the owner alive forever. Fix this for the following bindings by having the C++ side borrow the Python callables, and keeping them alive in a way the garbage collector can see: * DrakeLcmInterface borrows the handlers passed to Subscribe, SubscribeMultichannel, and SubscribeAllChannels. The DrakeLcm keeps each handler alive for as long as it lives, using ensure_callback_lifetime. DrakeLcmInterface is bound with dynamic_attr() to allow this. * DifferentialInverseKinematicsSystem::CollisionConstraint borrows the function passed to SetSelectDataForCollisionConstraintFunction. The ingredient keeps the current function in a single attribute, so that setting a new function releases the previous one. Passing None resets the function, as before. The Ingredient base class is bound with dynamic_attr() to allow this; the derived classes inherit it. The memory leak tests for these cases now require no leaks. New tests cover replacing and resetting the selector, and handlers that are not hashable.
* [fix] TBD [pydrake] Don't crash yaml_load on a root mapping with non-string keys ([#25245][_#25245])
* [fix] TBD [pydrake] Fix reference cycles in planning callbacks ([#25195][_#25195])  # Part of the issue "investigate uses of WrapCallbacks() for memory leaks". Python callables stored inside C++ objects are strong references that Python garbage collection cannot see, so a callable that captured its owner kept the owner alive forever. Fix this for the following bindings by having the C++ side borrow the Python callables, with various techniques for keeping them alive in a way the garbage collector can see. This uses make_arbitrary_callback_lifetime() for the cases where the nurse is created inside a binding. CollisionChecker and MultipleShooting are now bound with dynamic_attr() to allow this. The memory leak tests for these cases now require no leaks. Not addressed here: a distance function stored via CollisionCheckerParams still leaks.

# Notes


This release provides
[pre-compiled binaries](https://github.com/RobotLocomotion/drake/releases/tag/v1.59.0).
See [Installation](/installation.html) for instructions on how to use them.

Drake binary releases incorporate a pre-compiled version of
[SNOPT](https://ccom.ucsd.edu/~optimizers/solvers/snopt/) as part of the
[Mathematical Program toolbox](/group__solvers.html). Thanks to
Philip E. Gill and Elizabeth Wong for their kind support.
